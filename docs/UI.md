# hiveproxy 界面设计（2026-10-13 修订）

本文只管**界面**：信息架构、每页长什么样、每一项背后调哪个命令。
引擎与协议的设计仍在 [DESIGN.md](DESIGN.md)；本文第 5 节列出为支撑界面**必须**新增的引擎能力，
第 6 节记录与既有设计冲突时的取舍 —— 那几条是本文最该被质疑的部分。

本轮修订来自三条用户反馈（2026-10-13 问答确认）：

1. 首页要能**一眼配完**四件事：白名单端口、引导种子、出口探测加规则、代理端口；
2. 拓扑图里要能给节点指定**默认出口**，不命中规则时从它出去；
3. 现在的规则页**用不了** —— "行内要填的信息很抽象，保存还会报错"，
   期望是 **SwitchyOmega 那样**：条件在前、出口从下拉里选。

---

## 1. 信息架构

五个页面不变，改的是各自的职责与密度：

| 页面 | id | 这页回答的问题 | 本轮改动 |
| :--- | :--- | :--- | :--- |
| 首页 | `overview` | **我要怎么把它配起来** | 改为四张快捷配置卡 + 底部的运行指标 |
| 拓扑 | `topology` | 网里有哪些机器、我怎么到它们 | 节点表加「默认出口」列与一键设置 |
| 路由规则 | `rules` | 什么样的流量从哪儿出去 | 整页重做（SwitchyOmega 式） |
| 配置 | `config` | 全部参数（专家入口） | 不变 |
| 日志 | `logs` | 出什么事了 | 不变 |

**为什么首页不再以指标卡为主**：指标是"看"的，配置是"做"的。装完一台机器第一件要做的事是
把四个必填项填对（§10 的配置示例也只强调其中三项），指标卡在配好之前全是 `—`，占着首屏没有信息量。
指标本身没有删除，挪到首页底部，仍然一眼可见。

**为什么把"全部参数"留在配置页**：这四个快捷项之外还有四十多个参数（成本权重、gossip 半径、
认证令牌）。把它们平铺到首页会让首屏重新变成一堵墙 —— 而那是现在的毛病。

## 2. 首页：四张快捷配置卡

顶部一条**状态带**（不是卡片，是一行）：服务开关状态 · 本机地址 · 代理地址 · 直接链路数 ·
当前默认出口（点它跳规则页）。

状态带下面，**只在有东西可讲的时候**才出现一条提示：`已从「本机可直达网段」里排除：…`。
它回答的是"我明明在 10.x 里，为什么界面说我没有网段" —— 2026-10-13 用户撞到的正是这个：
`198.18.0.1/30` 是代理工具的 TUN 假地址池，被当成了真实网段（§18 第 33 条、DESIGN.md §9.1）。
**这类"软件替你做了判断"的事必须显式说出来**，否则用户只能去读源码。

### 2.1 ① 白名单端口

| 项 | 内容 |
| :--- | :--- |
| 字段 | `listen.ports`（`Vec<u16>`） |
| 控件 | 单个端口输入框 + 高级折叠（多个端口用逗号分隔） |
| 提示 | "IT 授权给这台机器的**入向端口**：别人就是拨这个端口找到你。必须与对端 `seeds` 里写的端口一致" |
| 生效 | **★ 改动需重启**（`listen.bind`/`ports` 只在进程启动时绑定） |
| 按钮 | 「保存」·「保存并重启」 |

用户反馈的原话是"我只需要定义其它机器能访问的白名单端口（一个就够了）"，2026-10-13 确认
指的是**入向监听端口**。它与 `share.share_ports_only`（我替全网连我网段里的哪些端口）含义相反，
所以两个都不会合并：快捷卡只放 `listen.ports`，`share_ports_only` 留在配置页。

### 2.2 ② 引导种子

| 项 | 内容 |
| :--- | :--- |
| 字段 | `peers.seeds`（三种写法：`ip:port` / `ip` / `ip:lo-hi`，§6.2.2） |
| 控件 | 输入框 + 「添加」；下面是已添加的列表，每行「移除」 |
| 生效 | 即时（拨号器下一轮巡检采用，无需重启） |
| 命令 | 已有 `add_seed` / `remove_seed`，不动 |

提示沿用现文案：跨网段的**第一条**链路只能靠它点火；接通之后监听端点广播会把其余候选自动补齐，
所以每台写 0~1 条就够。

### 2.3 ③ 出口探测 → 一键生成规则

这是本轮改动最大的一块。旧版"出口探测"只回一行文本：

```
目标      10.4.0.9:3389
出口      10.4.0.7
命中规则  内置网段兜底行
耗时      3 ms
```

它只回答了"**系统打算怎么办**"，不告诉你有别的选择、也不让你改。新版是：

```
目标 [ 10.4.0.9:3389        ] [探测]        ← 也可填域名；回车即探测

候选出口（按"自动选中的排第一，其余按成本"排序）
┌──────────────────────────────────────────────────────────────────────────┐
│ ● 自动选中  10.4.0.7（gpu-01）  直连 · 成本 1 · 声明 10.4.0.0/24  [实测] │
│ ○ 本机直连（目标就在我网段里）                                    [实测] │
│ ○ 10.0.0.1  2 跳 · 成本 8 · 未声明该网段                          [实测] │
└──────────────────────────────────────────────────────────────────────────┘
选中一条后：[生成规则]  [设为默认出口]        ← 目标与端口已经填好
```

- **候选集**＝所有当前可用出口 + 本机直连；每行标明**成本、跳数、是否声明过目标所在网段**。
  声明过目标网段的那一行会被标记（"它自己的网段里就有这个 IP"是最可靠的理由）。
- **实测**＝真的建一次流到目标再立刻关掉（`probe_dial`）。按钮上明确写"会真的建一次连接"，
  因为它是**唯一**能回答"这条出口真的够得着吗"的办法 —— 路由算得出来不代表防火墙放行、也不代表
  出口那一侧能连上目标。结果三态：`✓ 通了（18 ms）` / `✗ 出口拒绝：无路由` / `✗ 超时`。
- **生成规则**：把探测的目标拆成 host / port 预填进一条新规则的草稿，出口选中刚挑的那个，
  然后跳到规则页（草稿已经在那儿，用户改个备注就能保存）。
- **设为默认出口**：直接把该节点写进 `route.default_egress`（§4）。

**关于域名的一个必须讲清楚的坑**：`host` 是对**代理实际收到的目标**做的字面匹配。
浏览器一般自己在本地解析域名（SOCKS5 传的是 IP），所以"按域名写的规则"经常一条都命中不了。
探测卡要在探测目标为域名时显示一行提示：

> 这条目标以**域名**形式参与匹配。若客户端在自己的 DNS 上解析后把 IP 交给代理，
> 域名规则不会命中 —— 让客户端走 `socks5h`（代理侧解析）才会。探测结果里的
> "到达形式"会告诉你现在收到的是哪一种。

### 2.4 ④ 代理端口

| 项 | 内容 |
| :--- | :--- |
| 字段 | `proxy.socks5_bind`（`SocketAddr`，默认 `127.0.0.1:1080`） |
| 控件 | 端口输入框（bind 固定在 `127.0.0.1`，高级折叠里可改） |
| 提示 | 默认 **1080**；本机应用（浏览器、curl `--socks5-hostname`）连这个地址 |
| 生效 | **★ 改动需重启** |
| 按钮 | 「保存」·「保存并重启」 |

端口预填**当前值**而不是 1080。用户机器上现在的值是 1089（历史遗留），
所以卡片要给出「恢复 1080」这个明确的第二按钮，而不是悄悄改掉。

### 2.5 底部的运行指标

原来的 12 张指标卡与「活跃流」列表保留，折叠在「运行指标」面板里，默认展开。
指标口径不变，只把"本机可直达网段"这张宽卡保留在状态带里。

## 3. 规则页：SwitchyOmega 式

**形状直接照抄 SwitchyOmega 的「切换规则」那一页**（这是用户 2026-10-13 用截图给出的验收标准）：

```
排序 │ 条件类型 │ 条件设置 │ 出口 │ 操作
 ↕1  │ 域名后缀 │ *.corp.example.com          │ [节点 · 10.1.2.3（gpu-01）▾] │ ⋯ ✕
 ↑↓  │ 网段     │ 10.9.0.0/16:3306            │ [候选集 · db（3 个成员）▾]   │ ⋯ ✕
```

**一行只有三样要填**：条件类型、条件设置（**一个**框）、出口。别的什么都不在这一行里。

三条硬性排版规矩（都踩过一次）：

1. **同一行里所有控件同高** —— `--ctl-h`（30px），输入框/下拉/按钮一个都不例外。
   小按钮矮 10px 是"没对齐"的头号来源。
2. **单元格顶部对齐（`vertical-align: top`），不是中齐** —— `条件设置` 那格下面常有
   一行提示或红字，中齐会把它里面的输入框**整体抬高**，于是同一行的输入框与下拉看着就歪了。
3. **表头与单元格同一个内边距** —— 差 2px，表头文字与格子里第一个控件就不在一条竖线上。

第一版把它做成了 12 列的控件墙（启用 / host / 端口 / egress / 不可达 / 备注 / 命中 / 最近出口…），
用户的原话是"不知所谓" —— **控件越多，越看不出"这个目标从哪儿出去"这一件事**。所以这一节的
每条规矩都是在往回删东西。

### 3.1 概念对应

| SwitchyOmega | hiveproxy | 说明 |
| :--- | :--- | :--- |
| 情景模式 | **出口** | 一个出口 = 一个节点 / 候选集 / 直连 / 拒绝 / 自动 |
| 规则列表（条件 → 情景模式） | 规则表（条件 → 出口） | 都是**有序、先匹配者胜** |
| 默认情景模式 | **默认出口**（`route.default_egress`） | 不命中任何规则时用它（§4） |
| 条件类型 | **条件类型**（任意 / 域名后缀 / 精确主机 / 网段） | 与 `HostMatcher` 的四个变体一一对应 |
| 条件设置 | **条件设置**：一个框写 `host[:port]` | 端口折进同一个框，不另开一列（§3.2） |
| 自动保存 | **自动保存** | 引擎的 `set_rules` 本来就是整份替换，落盘 + 热生效（§3.5） |

**刻意不做**"命名情景模式"这一层。SwitchyOmega 需要它，是因为它的情景模式（代理服务器 A、
代理服务器 B）没有天然的名字；hiveproxy 的出口**本身就是可寻址的一等对象**（节点、别名、候选集），
再加一层命名就变成"名字 → 名字 → 节点"的两跳映射，而规则最需要的是"这条指向谁"一眼可见。
理由记在 §6。

### 3.2 条件：类型下拉 + **一个** 框

条件类型与引擎的 `HostMatcher` **一一对应，不多不少**：

| 条件类型 | 条件设置里写 | 存进引擎的 `host` |
| :--- | :--- | :--- |
| 任意 | （输入框禁用，显示"所有目标"） | `*` |
| 域名后缀 | `corp.example.com` 或 `*.corp.example.com` | `*.corp.example.com` |
| 精确主机 | `api.corp.example.com` / `10.1.2.9` | 原样 |
| 网段 | `10.9.0.0/16` | 原样 |

端口写在同一格里，**不写 = 任意端口**：

```
10.4.0.9:3389        10.9.0.0/16:8000-9000      *:443      [fd00::1]:443
```

输入框下面压一行小灰字，把这一行翻译成人话 —— 单框写法最需要的就是它：

> 域名后缀 corp.example.com 及其子域 · 任意端口

三条容易踩的规矩，都在 `src/lib/match.ts` 里：

1. **切换类型时值跟着转换**：`10.1.2.9` 切到"网段"会变成 `10.1.2.9/`（引擎随后提示缺前缀长度），
   切到"域名后缀"会变成 `*.10.1.2.9` —— 而不是悄悄换一种解释方式。
2. **只有"任意"能写成 `*`**。其余类型留空就留空，由引擎报"不能为空"。
   绝不能替用户补成 `*`：那会静默变成一条兜住全网的 `*:*` 规则（§17 风险 10 的警告就是这么来的）。
3. **空值 / 半成品靠"类型覆盖"钉住下拉框**：草稿里只有字符串，而空串解析回来永远是"任意"，
   所以刚切到"精确主机"还没填值时，靠 UI 的一份覆盖表把类型钉住，等填上值就自然一致了。

### 3.3 出口下拉：现场从拓扑生成

选项按组排列，每组都带"为什么选它"的现场信息：

```
自动（按网段就近，谁能到谁上）          → auto
本机直连（不进 overlay）                → direct
拒绝连接                                → block
── 节点 ──────────────────────────────────────────
10.4.0.7（gpu-01 · 直连 · 成本 1）       → node:10.4.0.7
10.0.0.1（2 跳 · 成本 8）                → node:10.0.0.1
── 候选集 ────────────────────────────────────────
db（显式定义 · 3 个成员）                → group:db
网段 10.9.0.0/16（自动派生 · 2 个声明者） → group:subnet:10.9.0.0/16
── 别名（仅本地规则）─────────────────────────────
gpu-01（peers.entry）                    → alias:gpu-01
── 其它 ──────────────────────────────────────────
手动填写…                                → 自由文本框
```

"其它"保留了全部表达能力（例如把节点写成裸 IP），但它不再是**唯一**入口 ——
这正是旧版"抽象"的根源。

### 3.4 表尾两行

表尾原本只有一行只读的"内置兜底行"。现在紧跟它多一行**默认出口**：

```
⤷  目标落在已知网段 → 选最近的声明者                [内置兜底 · 只读]
⤷  上面都没命中 → 默认出口：10.0.0.1                [在最上面那张卡里改]
```

顺序**就是** `resolve()` 的真实顺序（§4），两张表读起来应该跟代码一致。

### 3.5 自动保存（没有保存按钮）

SwitchyOmega 没有保存按钮，改完就是改完了 —— hiveproxy 照做：

- 编辑后 **600ms 静默**即存（引擎的 `set_rules` 本来就是整份替换 + 落盘 + 热生效）；
- 存之前先过 `check_rules`：**有行没填对就整份不存**，红字留在行内，
  引擎里仍然是上一次有效的那份（不会出现"半份规则生效"）；
- 面板右上角只有一个安静的状态字：`已保存` / `保存中…` / `有行没填对` / `服务未运行 · 改动待保存`；
- **服务没跑时不存**，也**不退化成直接写配置文件** —— 那会让没经过引擎校验的规则落进 TOML，
  下次启动直接解析失败。改动留在本地，服务一起来就自动补存；
- 请求飞在半空中时用户又改了 → **不清 dirty**，避免把刚敲的字当成"已保存"。

诚实的代价：打字中途停顿超过 600ms，会存下一个**中间态**（比如 `10.9.0.0/1`，它恰好是合法 CIDR）。
SwitchyOmega 也是这样，且引擎侧的热生效是即时的。真在意就先把条件写全再填端口的另一半。

**「+ 新增规则」新建的行是"待填"而不是 `*:*`**：条件设置默认给的是 `*.`（域名后缀、还没填后缀），
引擎因此回一句"`*.` 后必须有域名后缀" —— 行是红的、也就**不会被自动保存**。
如果默认成 `*:*`，那么"点一下新增、然后去接个电话"就会悄悄落一条兜住所有目标的规则进配置，
把共享规则整片遮住。想写"任意"可以显式在下拉里选，那时行内会出现一句黄色提醒
「⚠ 会兜住所有未被前面规则命中的目标」。

### 3.6 次要设置：收进「⋯」

启用 / 出口不可达时怎么办 / 备注，三样都要有，但都不该跟"从哪儿出去"抢位置，
所以收进每行的「⋯」，点开才出现，并顺带把引擎里的写法（`host = … port = … egress = …`）显示出来。

**命中统计不进编辑行**：它留在下面那张表里（"从来没命中"往往意味着写错了）。
规则不再是"一眼一行里塞八个数字"。

面板右上角的「说明」按钮展开一段长文案（本地优先于共享、不写规则也正常、条件设置的写法），
**默认收起** —— 一页说明文字摊在顶上，同样是"不知所谓"的一部分。

### 3.7 保留的既有能力

- 共享规则集横幅（来源、revision、发布时间、是否拒收）**常驻**（§9.4.3 的要求）；
- 「按具体度重排」「发布前预览」「一键发布到全网」「撤回共享」（都在表格**下方**，次要位置）；
- 规则命中统计、候选集（`group:`）面板；
- **全局旁路**在默认出口那张卡的右上角：它仍是排障用的紧急按钮，但不该跟编辑抢位置。
  开启时状态字与侧栏仍然显红。

### 3.8 行内校验

`check_rules` 收**原始行**（字符串形态），逐行解析，返回 `[{index, field, message}]`。
错误显示在**那一行**上，保存按钮自动变成"不存"。

这解决的是用户报的"保存还会报错"：旧版把整个草稿一次性丢给 `set_rules`，任何一行解析失败都是
一次**整体**失败，而错误来自后端反序列化，形如
`invalid args \`rules\` for command \`set_rules\`: 无法解析出口 ...` —— 既看不出是哪一行，
也看不出该怎么改。现在：错误在行内、保存前就已经指出，且 `set_rules` 本身也带行号
（"第 3 条：…"）作为兜底。

## 4. 默认出口（`route.default_egress`）

### 4.1 语义：最后兜底

```
规则表（本地 ++ 共享，先匹配者胜）
    ↓ 没有命中
内置网段匹配（目标落在已知网段 → 最近的声明者）
    ↓ 还是没人能去
默认出口
    ↓ 默认出口也不可用
NoRoute（SOCKS5 回 0x04）
```

**2026-10-13 确认**：默认出口排在网段匹配**之后**，而不是"没命中规则就一律走它"。
理由是这样才不破坏 §18 第 14 条（零配置合岛）：内网目标仍然自动就近走声明者，
只有"谁都不认识"的目标（域名、不在任何已知网段里的公网 IP）才落到默认出口 ——
而浏览器流量恰好几乎全是这一类。

### 4.2 配置形态

```toml
[route]
# 不命中任何规则、也不落在任何已知网段时，从哪个出口出去。
# 写法与规则的 egress 相同（§9.4.2 的取值表），但不接受 "auto"（那正是网段匹配本身）
# 与 "block"（那等于一键拒绝全部流量，误操作代价太大）。
default_egress = "node:10.0.0.1"
```

不可达时**不隐式改道**：默认出口已经是最后一顺位，没有"下一顺位"可退，直接回 `NoRoute`，
并在规则页那一行上显示"当前不可达"。

### 4.3 界面上在哪设

| 位置 | 形式 |
| :--- | :--- |
| 规则页表尾 | 一行下拉（§3.4） |
| 拓扑页节点表 | 多一列「默认出口」+ 行内按钮「设为默认出口」/「取消」 |
| 拓扑图 | 默认出口节点打一个徽标 |
| 首页状态带 | 显示当前值，点一下跳规则页 |

### 4.4 探测结果的"来源"

`StreamProbe` 现在只说"命中了第几条规则，或内置兜底行"。加了默认出口之后必须能区分三种来源，
否则探测会告诉你"内置网段兜底行"，而实际走的是默认出口。`Resolved` 增加
`MatchSource { Rule(idx), Subnet, Default }`（§5）。

**实测记录**（2026-10-13，用 `hiveproxy-cli` 起一个临时节点）：

```
① 不设默认出口   → curl --socks5-hostname → 127.0.0.1:11080 http://localhost:18081/  → 失败（curl rc 97）
② default-egress direct → 同一个请求 → 真实 HTML 返回 ✓
③ default-egress none   → 又失败 ✓
④ default-egress node:10.99.99.99（不可达）→ probe 明确报"无路由"，不偷偷改道 ✓
⑤ dial localhost:18081 via 127.0.0.1 → ✓ 本机直连成功
⑥ check-rules → 报出"第 1 条 · host：host 只写主机部分…" ✓
⑦ default-egress auto → "默认出口不接受 `auto` —— 那正是内置的网段匹配本身" ✓
```

**协议零改动**：默认出口是本机自己的决策，不进 gossip、不进帧头。

## 6. 取舍与自我质疑

1. **为什么默认出口不做成"表尾的一条规则"**：那样它会排在只读的网段兜底行**之前**
   —— 也就是把用户在问答里明确**否掉**的那个选项（"没命中规则就一律走它"）偷偷实现出来，
   还会破坏零配置合岛。做成独立字段后，"网段匹配在前、默认出口在后"是 `resolve()` 里显式的一步，
   谁想在将来改成"默认出口优先"都得改代码，而不是改一行配置顺序。
2. **为什么不做命名情景模式**（§3.1）：多一层映射，少一分可读性，而出口本身已经可寻址。
   如果将来出现"同一组出口要在十几条规则里复用"的实际痛点，再引入不迟 —— 那时它是一个
   `route.profiles` 表，`egress = "profile:work"` 一行语法，成本很低。
3. **为什么实测是按需而不是自动**：一次实测＝一次真实握手 + 出口侧一次真实 `connect`。
   自动全测会把探测从"瞬时"变成"数秒到数十秒"，并在网络上留下可观测的连接。
   按需实测把这笔成本交回给用户，且按钮上写明会发生什么。
4. **全局旁路为什么让位**：它是紧急按钮，不是日常按钮。但它的**状态**必须一直显眼 ——
   开着旁路时"我写的规则全都不生效"是最高优先级的解释，不能只藏在规则页角落里。
5. **为什么状态带不放进卡片**：四张卡片是"要做的事"，状态是"现在什么样"。混在一起会让
   "下一步该做什么"重新变得不明确。
6. **首页的指标卡没有删**：它们回答的是"跑得好不好"，与"配置"是两类问题；
   折叠而不是删除。
7. **规则页为什么只有五列**（2026-10-13 返工记录）：第一版做了 12 列（启用 / host / 端口 /
   egress / 不可达 / 备注 / 命中 / 最近出口），用户拿 SwitchyOmega 的截图回了一句"还是不知所谓"。
   教训值得写下来：**编辑行里每多一个控件，就多一分"这一行到底在说什么"的困惑**。
   同日第二轮反馈是"框框都没对齐，看起来很劣质"，对应的三条排版规矩写在 §3 开头 ——
   尤其第 2 条（顶部对齐）：它不直观，但改回中齐会立刻重新出现"输入框比下拉高一截"。
   运行期信息（命中、最近出口）属于下面的统计表；次要设置（启用 / 不可达 / 备注）属于「⋯」；
   长文案属于默认收起的「说明」。这三条界线以后再动这张表时请先看一遍。

## 7. 本轮不做

- SwitchyOmega 的**域名正则**条件（`HostMatcher` 没有对应变体；要加是一个枚举 + 一个下拉项，
  但没有实际需求驱动）；
- 只匹配域名 / 只匹配 IP 的条件类型（同上；常见需求由"默认出口"覆盖）；
- 规则的拖拽排序（保留 ↑↓ 按钮：拖拽要引依赖，而这个前端的一个硬约束是**离线可装**）；
- 出口的连通性**常态化**巡检（实测是手工动作，不做后台探测）。
